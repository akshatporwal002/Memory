# Engram UI audit — 7 September 2026

Engram needs a substantial interaction and hierarchy pass. Its warm palette, readable content surfaces, and native navigation are useful foundations. The main weakness is that the application combines several different product models: an editorial Today page, a phone deck gallery, a desktop note database, and two distinct deck creation flows.

## Scope and evidence

Audited the current working tree, including uncommitted UI additions, rather than only the committed version. Inspected navigation, Today, Library, deck creation, card editing, review/completion, Activity, settings, content rendering, and shared design tokens/components. Visually inspected the saved phone contact sheet at `design/previews/captures/phone-warm-light-mockup.png`. That image is an older illustrative mockup, not evidence of the current native app. Import/export and recovery workflows were not audited in depth.

Native simulator access timed out twice through computer use. No live interaction, VoiceOver, device-size, or performance claims are made. No application code or user data was changed. Source locations below refer to this working tree.

## Platform verdict and provisional score

The shell reads as a native SwiftUI application, not a ported website: TabView, NavigationStack, NavigationSplitView, native sheets, SF Symbols, and system text styles are already present. The main platform problems are inconsistent task behavior across widths, custom settings composition, and dismissal semantics.

These are provisional source-readiness scores, not measured usability or conformance results.

## Prioritized findings

### 1. P1 — Browsing a note unexpectedly enters editing

**Evidence:** `Sources/Features/LibraryScreens.swift:148–151`; `Sources/Features/EditorView.swift:45–59,68`.

At narrow widths, tapping a note calls `model.edit(note)`. At wide widths the same action selects a read-only detail. The editor then asks to discard on every Cancel and prevents swipe dismissal whenever a draft exists, even if nothing changed. A user simply inspecting an answer encounters an editing workflow and a loss warning.

**Change:** Make taps open card detail everywhere. Use a push on phone and the existing detail column on larger windows. Keep Edit explicit. Compare drafts with their original values so only actual modifications require discard protection.

**Acceptance:** Open and close an unchanged card without a discard prompt on phone, iPad, and Mac. Modified drafts remain protected. Resize without turning a reading task into editing.

### 2. P1 — Settings can silently lose unsaved changes

**Evidence:** `Sources/Features/SettingsView.swift:35–45,83–95,114–120`.

Appearance changes apply immediately, but study settings are staged behind a Save button. Done dismisses regardless of `changed`, and interactive dismissal is blocked only while busy. This creates two save models in one screen and permits unannounced loss of study-setting edits.

**Change:** Make Done validate and save staged settings before dismissal, or provide explicit Save/Cancel with dirty-state protection. Keep immediate appearance preferences clearly separated from staged study settings. Show an unambiguous saved state.

**Acceptance:** Change a daily limit, then use Done, swipe dismissal, and keyboard dismissal. Each path either preserves the edit or explicitly resolves unsaved changes; failed saves keep the screen open.

### 3. P1 — Accessibility gaps in the settings controls

**Evidence:** `Sources/Features/SettingsView.swift:51–55,68–75,183–199`.

Study controls always occupy two equal columns, including long labels and steppers, without checking available width or accessibility text size. The retention Slider has no label argument or explicit accessibility label; nearby visual Text does not establish a reliable semantic association.

**Change:** Use one native form row per setting on compact/large-text layouts, a labeled retention slider with a spoken percentage, and direct numeric entry for large daily limits. The existing stepper-only ranges extend to 10,000 and 100,000, making large adjustments laborious.

**Acceptance:** Largest accessibility text on a narrow phone retains every label, value, and control. VoiceOver identifies “Desired retention” and its percentage. Large limit changes do not require hundreds of button presses. Exact clipping and announcements remain runtime checks.

### 4. P2 — Today spends too much hierarchy on introduction

**Evidence:** `Sources/Features/LibraryScreens.swift:13–49`.

Today stacks a page title, full date, two-line slogan, queue label, large count, explanatory count breakdown, and study action. Resume is a separate secondary action below the main panel. The saved mockup also illustrates how much vertical emphasis the slogan and panel consume. The zero-ready state retains “READY WHEN YOU ARE” and sends users to “Check study queue.”

**Change:** Lead with the actual state: Continue review, cards ready, or caught up. Give that state one dominant action. Reduce the slogan to onboarding or a small occasional completion message. Put due decks immediately below; move persistent backup explanation into a useful backup entry point in Settings.

**Acceptance:** First viewport answers “What should I do now?” for new users, returning sessions, ready cards, daily limits, and no ready cards. Never display invented study-time or retention estimates.

### 5. P2 — Deck creation changes meaning by entry point

**Evidence:** `Sources/Features/LibraryScreens.swift:20,39`; `Sources/Features/EngramRootView.swift:164`; `Sources/Features/LibraryLandingView.swift:57–66`; `Sources/Features/DeckCreationView.swift:33–79`.

Today opens the small DeckForm flow; phone Library opens a document composer that can generate multiple cards. This makes the same “New deck” task behave differently depending on where the user starts. The newer composer is also unavailable through the iPad/Mac Library branch.

**Change:** Route all New deck actions through one shared creation model. Begin with name and optional folder, with clear choices to add cards individually or paste questions. Preserve the useful document composer as a visible bulk-entry mode. Adapt its presentation to the platform.

**Acceptance:** A new deck has the same capabilities and draft behavior from Today, Library, and larger-screen navigation.

### 6. P2 — Library is a different product across devices

**Evidence:** `Sources/Features/EngramRootView.swift:118–127`; `Sources/Features/LibraryLandingView.swift:85–143`; `Sources/Features/LibraryScreens.swift:118–139`.

Phone users get deck covers, sorting, folders, and a gallery/list toggle. iPad and Mac users enter a note list with a deck picker instead. The phone collection also spends multiple rows on search, view mode, sorting, and a full-width folder switch before reaching content.

**Change:** Share a deck collection and selection model across platforms. Keep search prominent; combine sort, grouping, and display choices into a compact view-options menu. Use desktop space for a deck sidebar, notes column, and detail pane. Preserve platform-specific layout while keeping the same task vocabulary and capabilities.

**Acceptance:** Find a deck, change grouping, and inspect its cards on every platform without relearning the feature. Check compact iPad windows as well as full screen.

### 7. P2 — Note rows expose too much scheduling machinery

**Evidence:** `Sources/Features/LibraryScreens.swift:154–170,183`.

Each note row contains raw `note.front`, type, tags, and every generated card’s state plus a Suspend action. Cloze notes can produce tall repetitive rows. Raw cloze or imported markup can appear in the preview text. The search placeholder teaches query syntax before the user asks for it.

**Change:** Use a sanitized readable prompt excerpt, one concise status summary, and an optional tag line. Move per-card scheduling and suspension into card detail/context actions. Offer visible filters such as Due, New, and Suspended while retaining advanced query syntax in search help.

**Acceptance:** A multi-cloze note stays easy to scan; supported formatting does not leak as markup. Advanced management remains available within a short action path.

### 8. P2 — Card authoring requires too much syntax and form work

**Evidence:** `Sources/Features/EditorView.swift:76–110,127–133`.

Cloze creation depends on manually typing special syntax. Tags, source, and scheduling caveats are always expanded. Preview always uses the prompt typography, while Review switches long prompts to body typography, so authoring can misrepresent the final reading experience.

**Change:** Make Question and Answer the primary form. Put tags and source under optional details. Add a “Hide selected text” cloze action with generated-card preview and inline syntax feedback. Share prompt typography selection with Review. Keep manual syntax for experienced users.

**Acceptance:** Create a basic card with no need to inspect optional fields. Create a cloze without memorizing delimiters. Long prompts look consistent in Preview and Review; switching modes preserves draft and focus appropriately.

### 9. P2 — Activity reports events without explaining progress

**Evidence:** `Sources/Features/LibraryScreens.swift:246–267`.

Activity has two counts and up to 100 review events, identified by grade and deck rather than card. It does little to answer when the user studied or which deck needs attention.

**Change:** Lead with an accessible weekly review histogram, days studied, unique cards reviewed, and a per-deck summary. Keep detailed events in a secondary list with recognizable card text and navigation to detail. Treat imported evidence separately where aggregation semantics differ. Avoid claiming measured retention or mastery from review counts.

**Acceptance:** Every summary is derived from persisted records, respects the configured study-day boundary, and has a text equivalent. Empty history shows a useful first-study action.

### 10. P2 — Review can be more focused and context-sensitive

**Evidence:** `Sources/Features/ReviewView.swift:23–28,46–47,81,89–109`.

The core reveal/grade flow is sound. However, “Space to reveal” is always shown, including touch-only use, appearance switching occupies review chrome, and all prompts inherit a fixed minimum 280-point surface. The saved mockup emphasizes a large ornamental card and substantial blank space; current source geometry requires native inspection before judging exact proportions.

**Change:** Keep the persistent grading area and explicit reveal. Use a quiet deck/progress header, move appearance out of the main study toolbar, show keyboard hints where relevant, and adapt prompt spacing to content length and available height. Reserve control space so reveal does not produce a distracting jump.

**Acceptance:** Short questions feel intentional; long answers and images remain readable. Landscape and accessibility-size grade controls leave a usable scrolling content region. Undo and persistence behavior stay intact.

### 11. P2 — Repeated work threatens responsiveness as libraries grow

**Evidence:** `Sources/Features/EngramModel.swift:61–68`; `Sources/Features/LibraryScreens.swift:146–169,259`; `Sources/Features/CardContentView.swift:84–100`.

View evaluation calls note-to-card filtering repeatedly, Activity sorts all active reviews before taking 100, and image loading begins synchronously in view lifecycle callbacks. These are source-level scaling risks; no dropped frames or latency were measured.

**Change:** Build revision-keyed lookup indexes and summary snapshots, compute bounded recent activity outside repeated body evaluation, and move image decode work off the UI thread with cancellation and caching. Measure before pursuing further optimization.

**Acceptance:** Profile a representative large library and image-heavy review session on Apple hardware. Search, scrolling, and grading stay responsive; summaries refresh correctly after mutation. Do not infer performance from mockups or backend tests.

### 12. P3 — Surface and typography roles need a consistent hierarchy

**Evidence:** `Sources/DesignSystem/EngramComponents.swift:44–60`; `Sources/DesignSystem/EngramTokens.swift:15–20`; `Sources/DesignSystem/EngramTheme.swift` typography mapping; `Sources/Features/LibraryLandingView.swift:88,117,214`.

The shared surface modifier applies the study-card corner radius and shadow to all callers. New Library uses separate literal radii and bold system headings, while older sections use serif display roles. The saved contact sheet feels uniformly rounded and softly outlined, reducing distinction between reading content, form fields, and navigation.

**Change:** Define separate reading surface, collection item, form field, and settings-group treatments. Use serif sparingly for an intentional display moment; use system sans-serif for dense navigation and controls. Reduce unnecessary borders/shadows while retaining accessible input boundaries. Preserve warm ivory/olive and the neutral theme.

**Acceptance:** Users can visually distinguish editable fields, tappable collection items, and passive reading content without relying on text alone. Validate actual color pairings in both appearances.

## Recommended design direction

Make Engram a calm, precise study workspace. Today should behave like a daily agenda. Library should feel like a coherent collection. Card detail should support reading before editing. Review should give almost all attention to recall, answer, and grading. The editor should make a single useful card fast to create, while keeping bulk entry and advanced syntax available.

The redesign does not need more gradients, decorative charts, glass-covered content, or animated card flips. Its distinctiveness can come from typography, excellent spacing, compact useful summaries, and consistent interaction behavior.

Keep the existing native navigation, semantic text styles, warm/neutral appearance support, reduced-motion behavior, explicit reveal, labeled grading intervals, safe-area control placement, and review undo.
